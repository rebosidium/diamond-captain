# Define ↘ · Problem

Choose the problem worth solving, its scope and the change that would count as useful. Ask: whose need is supported, what matters most, and what would overturn this framing? Reuse discovery evidence; investigate only gaps that affect the choice.

| Question or gap | Candidate | Prefer when… |
| --- | --- | --- |
| Why does this distinction matter? | [QL-10 Laddering interview](qualitative.md#ql-10) | A concrete attribute can be traced to consequences and valued outcomes. |
| How do people understand the domain? | [QL-14 Cognitive mapping](qualitative.md#ql-14) | Relationships, boundaries or competing mental models need clarification. |
| Which events shape the problem? | [QL-19 Experience timeline](qualitative.md#ql-19) | Experiences cross channels and retrospective gaps need surfacing. |
| Which accounts are missing? | [QL-18 Open-response survey](qualitative.md#ql-18) | Independent written experiences can broaden understanding; follow-up depth is limited. |
| How often does the problem occur? | [QT-02 Rate estimation](quantitative.md#qt-02) | Eligible units, outcomes and missing cases can be defined. |
| How long until an outcome? | [QT-07 Time-to-event analysis](quantitative.md#qt-07) | Some cases remain unfinished; excluding them would bias duration estimates. |
| Is the delay waiting or processing? | [QT-08 Queue/service-time analysis](quantitative.md#qt-08) | Arrivals, handoffs, handling and outstanding work can be distinguished. |
| How common is a reported experience? | [QT-09 Sampled survey estimation](quantitative.md#qt-09) | A defensible population, sample and question wording are feasible. |
| Are we solving the right problem? | [DS-02 Alternative framing](design-and-delivery.md#ds-02) | A request assumes a cause or embeds a preferred solution. |
| What outcome should this change affect? | [DS-03 Outcome chain](design-and-delivery.md#ds-03) | Activities or proxy metrics are being mistaken for user value. |
| What operations create the visible experience? | [DS-05 Service blueprint](design-and-delivery.md#ds-05) | Backstage work and handoffs affect the problem boundary. |
| Can the direction be sustained? | [DS-13 Viability stress check](design-and-delivery.md#ds-13) | Staffing, support costs or ownership could make the scope untenable. |

A useful handoff is a supported problem, affected roles, intended outcome, boundaries, baseline or measurement gap, and owner/decision. Do not convert a convenient survey into a population estimate or a diagram into observed evidence. Keep rejected framings and unresolved assumptions in the existing checkpoint; method completion does not accept the brief.

For several problems competing for capacity, use [cross-task priorities](../portfolio-and-priority.md); the human chooses which task proceeds.

For conflicting interests or required sign-off, use the [stakeholder map and decision path](../stakeholders.md).

When a change can shift harm or effort to others, use the [harm and risk review](../harm-and-risk.md); mandatory controls still apply.
